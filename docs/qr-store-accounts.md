# MARUGO QR 店舗別アカウント

## 利用手順

- MARUGOの入口でMARUGO QRを選び、メールアドレスでログインする。
- 新規登録では所属店舗を選ぶ。所属は「申請」であり、即時の閲覧権限ではない。
- メールを送った同じブラウザー・端末で確認リンクを開く（PKCE）。管理者がメール確認済みの所属を承認してから利用可能。
- 既存Supabaseアカウントはそのメール・パスワードでログインし、QRの所属店舗を初回申請する。重複登録で権限・所属は変更されない。
- パスワードを忘れた場合はメールを送り、同じブラウザーで再設定リンクを開く。期限切れの場合は再送する。
- 同じSupabaseプロジェクトのレシピアプリと同一メールを使う場合、Authのパスワード変更はそのアカウントにも適用される。kotonohaの共通IDは変更しない。

## 権限・データ境界

`Auth本人確認 → QR所属/利用状態 → 店舗ID検証 → QR/履歴/ファイル操作`

メール確認と管理者承認の両方が必要。一般メンバーは所属店舗だけ、全店舗管理者は全店舗と「未割当（旧QR）」を切り替えて管理する。QR・履歴・分析・ファイル・ゴミ箱すべてが同じ店舗境界を使う。店舗を変えると表示を破棄して再取得する。

店舗名は11店舗のマスターを初期登録。「マルゴ ヨツヤ」は使わず「マルゴ四谷」に統一。既存QRは従来の所有ID・コード・履歴・ファイルパスを変えず未割当に保持する。店舗変更はアカウントの所属変更であり、既存QRを移動する操作ではない。

pingus0428@gmail.comの既存・確認済みAuthユーザーだけを初期管理者にする。QRの権限は新しい専用テーブルに格納し、他アプリのprofiles/roleは変更しない。新規Authユーザーには既存のレシピ用profile作成トリガーも従来どおり実行される。

全店舗管理者は登録IDとメール・所属・状態を一覧管理し、所属承認/再開・停止・所属変更・管理者付与/取り消しが可能。対象と影響を確認するダイアログを必須にする。本人の設定変更を禁止し、管理者を最後の1人まで取り消さない。権限操作はDBロック内で再検証・監査記録を保存する。

## 本番設定の必須確認

Supabase Authの既存Site URL/他アプリのURLを変更せず、Redirect URLsに次の2件を追加する。

- `https://marugo-s.github.io/multiapp/?account=confirm`
- `https://marugo-s.github.io/multiapp/?account=recovery`

既存メールテンプレートが標準の `{{ .ConfirmationURL }}` / `{{ .RedirectTo }}` を尊重することを確認する。カスタムSMTPが必要（標準送信サービスではプロジェクトのチーム以外への送信に制限がある）。設定のためにメール確認を無効化しない。共有プロジェクトのSMTP・テンプレート変更は他アプリにも影響するので別途確認が必要。

### 日本語の認証メール（文面用意済み・本番設定は別途）

Supabase Dashboard → Authentication → Emails で件名・本文を変更する。プロジェクト共通のためMARUGOブランドで、アプリ固有の所属承認を本文に混ぜない。

| 種類 | 件名 | 本文ファイル |
| --- | --- | --- |
| Confirm signup | 【MARUGO】メールアドレスの確認 | `supabase/templates/confirmation-ja.html` |
| Reset password | 【MARUGO】パスワードの再設定 | `supabase/templates/recovery-ja.html` |

確認ボタンの `{{ .ConfirmationURL }}` は置換しない。メールテンプレートをGitで保存するだけではクラウド設定へ反映されない。SMTP、戻り先、件名・本文を確認し、実際にメールが届いてこのアプリへ戻るまで確認する。

## 実装・検証

- service_roleだけが専用RPCを実行可能、専用テーブルはRLS有効・anon/authenticatedの直接権限なし。
- EdgeはAuth `/user` でJWTを検証し、クライアントのuserId/role/ownerIdを信頼しない。旧ktnトークンでQR管理へ入れない。
- AuthコールバックはQR転送より優先し、URLの認証コードを消去し、no-referrer/noindexを設定する。
- 公開QR/PDF閲覧はこれまでどおり。管理画面の所属分離とは別に、公開リンクを知る人は公開ファイルを閲覧できる。
- Node callback/bootstrap/path tests、Deno Edge tests、`tests/qr-accounts.sql`（ランダムfixturesのみ・rollback）で確認する。

## トレードオフ

店舗自己申告を即時権限にしないため管理者承認が必要。PKCEは確認メールを別端末で開くと利用できないが、認証コード単独の盗用を防ぐ。静的GitHub PagesのためAuth・権限・データ処理はSupabase側で行う。大規模化時は管理者用MFA、招待方式、CAPTCHA、店舗マスター管理、監査画面とメール送信監視を追加検討する。

2026-10-07から、入口の通常フォームはkotonohaと共通のID・パスワードを利用します。有効な共通セッションは全店舗・旧QR・QRアカウント管理を利用できます。以下の個別アカウント機能は「別の方法でログイン」から引き続き利用できます。個別アカウントの所属・承認・停止は共通IDの利用権限に影響しません。正式運用へ切り替える際はREADMEの手順で共通QR利用を停止してください。
